## Scoring and submission

The scorer applies each generated patch to a repository snapshot and runs the task's validation tests. The score is the fraction of tasks resolved. The submission is a ZIP containing declarative agent configuration, with exactly one root `agent.yaml` and optional prompts, subagents, skills, and LoRA adapters. The private leaderboard determines final placement; exact-score ties go to the submission entered first.

The official overview gives the agent 12 hours to submit patches across the test set, including sandbox setup but excluding patch validation. Kaggle staff estimate validation can add about two hours when every task has a patch; a no-patch run takes about ten minutes. Participants later reported scoring taking several hours, around 12 hours in one case, and timing out after 14 hours in another; treat those as anecdotes, not an SLA ([official overview](https://www.kaggle.com/competitions/gemma-4-developer-agent/overview), [staff clarification](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/743663), [rerunning failed submissions thread](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/743683)). A per-task time cap must fit inside that global limit, so extrapolate local task runtimes cautiously.

Kaggle staff confirmed the thinking-token loss between tool calls was a harness incompatibility and said the fix should be in the current wheelhouse. Since candidates enable thoughts, record the wheelhouse/runtime version for future comparisons ([discussion](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/744354)).

The competition supports `gemma-4-31b-it-qat-w4a16-ct`, `gemma-4-12b-it-qat-w4a16-ct`, `gemma-4-e4b-it-qat-w4a16-ct`, and `gemma-4-e2b-it-qat-w4a16-ct`. All agents in a submission must use the same base model. E2B and E4B submissions remain eligible for the general leaderboard and can also qualify for the $10,000 small-model bonus if selected as one of the team's two final submissions; an official notebook publishes filtered daily standings. The submission is a ZIP with a root `agent.yaml`; the 3 GiB unpacked archive limit and sandbox restrictions apply.

The official overview lists $65,000 for the main competition, $35,000 for the optional paper track, and a $10,000 small-model bonus. The final submission deadline is 2026-12-02 23:59 UTC; the entry/team-merge deadline is 2026-11-25 23:59 UTC.

## Harness findings that affect experiments

- The graph tools are registered and conditionally advertised when the task's graph and embedding assets are present. The local guide documents `get_code_neighbors`, `search_similar_code`, and `get_code_subgraph`. A Kaggle participant replay found that graph-query yield changed across wheelhouse builds: 11/314 calls on one intermediate build versus 270/314 on each of v0.2.10 and v0.2.11. The wheelhouse dataset metadata currently reports an update on 2026-10-12, so the reference prompt's blanket ban on graph tools should be treated as unverified ([discussion](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/748323)).
- A participant reported a vLLM 0.19.1 Gemma tool-parser hang when an array argument contains a JSON-style quoted string with `]`; the report's minimal reproduction stalls `_parse_gemma4_args`, and one validation run reportedly left later tasks timing out without LLM calls. The report has no visible staff response or fix as of 2026-11-19 ([Kaggle discussion](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/753973)). The upstream vLLM project documents the same malformed-array loop and says it was fixed in v0.21.0 ([vLLM issue #51284](https://github.com/vllm-project/vllm/issues/51284)); do not assume that fix is in the competition wheelhouse reported as v0.19.1. In this harness, `get_code_subgraph(nodes: list[str])` is the graph tool with an array argument. Expanded task `fastapi_14616` includes the literal `Json[list[str]]`, so the report is relevant to the planned graph-enabled ablation. The current reference prompt bans graph tools; keep that baseline unchanged, and audit graph traces for malformed `get_code_subgraph` calls before using the result to justify a public submission. This is a participant-reported infrastructure risk, not a confirmed scorer-wide failure.
- `submit_patch()` ends the agent loop. If the agent does not call it, the harness can capture a fallback diff; still call it last after the change is ready.
- Test and runner-config edits are removed before verification, so use tests as read-only requirements and patch product source.
- The local harness supports `max_tool_calls`, `max_time_minutes`, `max_turns`, and command timeout settings under `eval_config.yaml`.
- The dataset and README can lag discussion updates. Re-check the current competition page/discussion before locking model support or scorer assumptions.
