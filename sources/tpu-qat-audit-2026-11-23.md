# TPU feasibility audit: Gemma 4 31B QAT W4A16

Checked 2026-11-22 20:50 UTC. This is a runtime feasibility check, not competition scoring evidence.

## Result

**NO-GO for evaluator work until the model-load/text/tool-call smoke passes; TPU results are not comparable to NvidiaL4 evaluations.** Official vLLM JAX code supports the relevant QAT linear-layer format and has served Gemma 4 31B QAT W4A16 on one v6e chip. The exact Kaggle setup remains only partially validated: it uses TPU v5e-8 and tensor parallelism 8, while the upstream implementation author explicitly says v5e and tensor parallelism above 1 were untested. Let the existing smoke answer that question before spending TPU quota on an evaluator probe.

## Evidence

- Google's [Gemma QAT guide](https://gemma.ai/get-started/qat/) maps `-qat-w4a16-ct` to vLLM/SGLang and lists 31B as an available size. The Kaggle competition's allowed model is the same named checkpoint; the private notebook metadata attaches `google/gemma-4/Other/gemma-4-31b-it-qat-w4a16-ct/2`.
- The official [vLLM JAX PR #3653](https://github.com/vllm-project/tpu-inference/pull/3653) adds compressed-tensors W4A16 linear support for symmetric int4, `group`/`channel`, `pack-quantized` checkpoints. It reports that 31B served on one v6e chip, but explicitly says v5e and TP>1 were untested; its measured serving setup took about 27 minutes to cold-compile 31B. The change was merged Sep 27 and included in the v0.31 release; the currently pinned [v0.33.0 release](https://github.com/vllm-project/tpu-inference/releases/tag/v0.33.0) is newer.
- The [vLLM JAX support matrix](https://github.com/vllm-project/tpu-inference/blob/61899c6dff45253fd69b71acda7de425ad5345f6/README.md) lists v5e as a recommended TPU generation, and lists single-host tensor parallelism for the Flax/JAX path. However, its quantization table does not list compressed-tensors INT4 W4A16 as a validated checkpoint format (it lists AWQ INT4 and compressed-tensors FP8). Thus the release/merged implementation evidence is stronger than the matrix's explicit validation status, but neither establishes the exact v5e-8/TP8 run.
- The current [vLLM JAX out-of-tree guide](https://github.com/vllm-project/tpu-inference/blob/main/docs/getting_started/out-of-tree.md) shows an example with `--max-model-len=1024`, `--tensor-parallel-size 8`, `--max-num-batched-tokens 1024`, and `--max-num-seqs=1`. This is a configuration example, not validation of the competition's QAT checkpoint.
- Upstream [issue #3225](https://github.com/vllm-project/tpu-inference/issues/3225) reports an older E2B/E4B-specific QAT loading failure for KV-shared layers and a separate W4A16 scheme-resolution failure. The competition's 31B model has no KV-shared layers; PR #3653 subsequently added the JAX W4A16 linear method. Do not transfer that old E2B/E4B failure directly to this 31B setup.

## Version 6 memory-lever assessment — checked 2026-11-26 08:08 UTC

One targeted setup smoke is justified; evaluator work remains blocked until it passes.

- **Observed pressure:** version 5 reported total TPU HBM of 125.98 GiB, a 115.91 GiB limit cap, 22.03 GiB already used after weight loading, and 93.88 GiB available before KV-cache initialization. It then initialized the KV cache at 14.49/15.75 GiB per chip. The failing compile requested 16.87 GiB per chip, including a 2.64 GiB program, exceeding physical HBM by about 1.12 GiB in the compiler's allocation summary (the terminal error reports 898.41 MiB over). This points to cache allocation leaving too little space for compile-time buffers.
- **Supported lever:** the pinned vLLM JAX `v0.33.0` worker computes its device-memory cap as `total_hbm_limit * gpu_memory_utilization` and reports the remainder after existing allocations as available for the cache. Its pinned vLLM LKG sets the default to `0.92` and documents that this fraction also applies on non-GPU devices ([TPU worker source](https://github.com/vllm-project/tpu-inference/blob/v0.33.0/tpu_inference/worker/tpu_worker.py#L468-L520), [pinned cache config](https://github.com/vllm-project/vllm/blob/7b77ed581d/vllm/config/cache.py#L196-L205)). Version 6 sets `--gpu-memory-utilization 0.70`, lowering the calculated cap from about 115.91 to 88.19 GiB total. Inference from that cap: the KV-cache budget should fall by about 27.72 GiB total (about 3.47 GiB per chip), leaving materially more room for compile buffers; the smoke needs only one 2,048-token request. The estimate is not runtime evidence.
- **Why the earlier knobs did not decide this:** lowering `max-model-len` from 4096 to 2048 left the OOM essentially unchanged. Version 5's `max-num-seqs=1` already produced a one-request backbone compile. `max-num-batched-tokens` does set the largest token bucket: the pinned runner caps precompile buckets at `max_num_batched_tokens * dp_size`, and the compilation manager precompiles each bucket ([TPU runner source](https://github.com/vllm-project/tpu-inference/blob/v0.33.0/tpu_inference/runner/tpu_runner.py#L1010-L1052), [compilation manager](https://github.com/vllm-project/tpu-inference/blob/v0.33.0/tpu_inference/runner/compilation_manager.py#L679-L735)). Lowering it to 512 remains a reasonable fallback if the cache-budget smoke still OOMs, but the current memory report makes KV-cache headroom the more direct first variable to isolate.
