## Scoring and submission

The scorer applies each generated patch to a repository snapshot and runs the task's validation tests. The score is the fraction of tasks resolved. The submission is a ZIP containing declarative agent configuration, with exactly one root `agent.yaml` and optional prompts, subagents, skills, and LoRA adapters. The private leaderboard determines final placement; exact-score ties go to the submission entered first.

The official overview gives the agent 12 hours to submit patches across all test tasks, including sandbox setup but excluding patch validation. Kaggle staff estimate validation can add about two hours when every task has a patch; a no-patch run takes about ten minutes. Participants later reported scoring taking several hours, around 12 hours in one case, and timing out after 14 hours in another; treat those as anecdotes, not an SLA. On 2026-11-24, participant `renxiaohan` reported submission 58789980 exceeded the allowed runtime despite an eight-minute per-task cap; the thread had no replies at 13:58 UTC. This is not a confirmed scorer failure mode, but it reinforces that a per-task cap does not guarantee the global limit. For scale, 120 tasks at the eight-minute cap is a 16-hour worst case before any separate overhead ([official overview](https://www.kaggle.com/competitions/gemma-4-developer-agent/overview), [staff clarification](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/743663), [rerunning failed submissions thread](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/743683), [runtime report](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/761467)).

In its 2026-11-19 queue update, Kaggle reported average notebook runtimes of about 9–10 hours, preceded by 8–9 hours in queue and followed by 2–2.5 hours of scoring; about 94% completed in under 24 hours, typically in 20–24 hours end-to-end. Later forum comments are participant reports, not a revised Kaggle estimate. The latest queue reports and their limitations are in the [submission queue audit](submission-queue-audit-2026-11-25.md).

A separate participant report says a notebook spent five hours queued and five hours running, with ten GPU quota hours deducted. The [competition overview](https://www.kaggle.com/competitions/gemma-4-developer-agent/overview) specifies that L4×4 notebooks consume GPU quota at twice the rate of older T4×2/P100 machines. Our 2026-11-21 V5 44-task run is consistent with that rate: its log spans 11,629 seconds (3.23 hours), while quota rose from 8.34h to 12.66h used during a 2h10m interval when the kernel was recorded as `RUNNING` (4.32 quota hours, about 1.99×). Thus the reported ten-hour deduction is consistent with five hours of L4×4 runtime at the 2× rate; it does not establish that queued time was charged. Queue-time quota accounting remains unverified. Use actual `kaggle quota` readings after each run and keep the 72-hour final-upload buffer as a minimum ([organizer queue update](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/760471), [L4×4 queue discussion](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/743683)).

The organizer confirmed on 2026-11-20 that the rescore after fixing an exploit in the metric was complete and that the patch affected exploits, not standard agent behavior. Use current leaderboard snapshots rather than pre-rescore score reports ([rescore discussion](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/760126)).

Kaggle staff confirmed the thinking-token loss between tool calls was a harness incompatibility and said the fix should be in the current wheelhouse. Since candidates enable thoughts, record the wheelhouse/runtime version for future comparisons ([discussion](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/744354)).

The public wheelhouse API still reports an October 12 version. An audit of its exact vLLM wheel found no `reasoning_content` normalization in `ChatCompletionRequest`, while upstream PR [#42664](https://github.com/vllm-project/vllm/pull/42664) adds that normalization before message validation. Kaggle staff said the fix should be in the current wheelhouse, but the scorer's deployed build is unverified. Record whether the compatibility shim was applied and treat local comparisons as training-task evidence; see the [wheelhouse audit](wheelhouse-audit-2026-11-23.md).

The competition supports `gemma-4-31b-it-qat-w4a16-ct`, `gemma-4-12b-it-qat-w4a16-ct`, `gemma-4-e4b-it-qat-w4a16-ct`, and `gemma-4-e2b-it-qat-w4a16-ct`. All agents in a submission must use the same base model. E2B and E4B submissions remain eligible for the general leaderboard and can also qualify for the $10,000 small-model bonus if selected as one of the team's two final submissions; an official notebook publishes filtered daily standings. Kaggle allows at most one public submission per day and up to two final submissions ([official rules](https://www.kaggle.com/competitions/gemma-4-developer-agent/rules)). The submission is a ZIP with a root `agent.yaml`; the 3 GiB unpacked archive limit and sandbox restrictions apply.

The official overview lists $65,000 for the main competition, $35,000 for the optional paper track, and a $10,000 small-model bonus. The final submission deadline is 2026-12-02 23:59 UTC; the entry/team-merge deadline is 2026-11-25 23:59 UTC.

## Harness findings that affect experiments

- The graph tools are registered and conditionally advertised when the task's graph and embedding assets are present. The local guide documents `get_code_neighbors`, `search_similar_code`, and `get_code_subgraph`. A Kaggle participant replay found that graph-query yield changed across wheelhouse builds: 11/314 calls on one intermediate build versus 270/314 on each of v0.2.10 and v0.2.11. The wheelhouse dataset metadata currently reports an update on 2026-10-12, so graph-tool usefulness remains version-sensitive ([discussion](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/748323)).
- The competition wheelhouse reports vLLM 0.19.1, whose legacy Gemma parser can loop forever on a malformed array argument: `_parse_gemma4_array` stops before a `]` inside a plain JSON-quoted element, then does not advance at that same bracket. Upstream issue [#51284](https://github.com/vllm-project/vllm/issues/51284) reproduces this on stock 0.19.1 and says the guard was first shipped in v0.21.0; the current upstream parser includes a no-progress guard ([source](https://github.com/vllm-project/vllm/blob/main/vllm/parser/gemma4.py)). A Kaggle participant reported the same freeze in the competition runtime ([discussion](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/753973)). `get_code_subgraph(nodes: list[str])` exposes the relevant array shape. The current V5 prompt prohibits graph calls, and an audit of 91 available V5 traces found no graph-tool calls among 2,284 tool calls; this local evidence does not establish behavior on hidden tasks. Keep the pending V5 submission unchanged. The current-wheelhouse gold/empty control qualified 53 task IDs; use that same set for the seed-42 V5 and no-graph comparisons after quota refresh. Inspect traces before any graph-enabled experiment. Treat an inference hang as a runtime failure, not a low agent score.
- Purnima Pathak's [public scorable-task audit](https://www.kaggle.com/code/purnimapathak15/score-gemma4-agent-on-72-scorable-tasks) and [CC BY 4.0 dataset](https://www.kaggle.com/datasets/purnimapathak15/gemma4-agent-selftest-scorable-tasks-and-traces) use gold-patch and empty-patch controls to identify 72 locally scorable tasks among the 129 public training tasks. The original 54-task candidate appended ten Rich tasks to the 44-task verified training core and remained disjoint from the 18-task holdout. The control results are external evidence, not our agent scores; see the [task-set audit](scorable-task-set-audit-2026-11-23.md).
- Kaggle staff later said the scorer's test tasks are from repositories absent from the public training set, that the training-task set is being fixed, and that every test task passes with a gold patch ([discussion #747248](https://www.kaggle.com/competitions/gemma-4-developer-agent/discussion/747248)). Participants independently reproduced only 43/129 gold-patch passes with a public Docker setup and reported Python/Pydantic dependency and package-shadowing failures; those are training-harness diagnostics, not evidence about the scorer's test environment. A paired control of our 54-task candidate against the current wheelhouse completed at 53/54 gold passes and 0/54 empty passes.
